### Phase 3 — Run Research (2026-05-18)

Dispatched 1 light-touch survey agent. Findings (per evidence-flagged report):

- **scikit-learn / pandas**: per-version Sphinx rebuild, each release gets its own `whats_new/v<X.Y>.rst`; contributing-guide rule is "never modify existing reference labels" — i.e., manual discipline + PR review, no documented rewrite tooling.
- **mike (mkdocs)**: "once a version is built, never touch it again"; no in-content cross-version reference mechanism — explicitly punts to users.
- **SQLAlchemy**: per-version doc sites at `docs.sqlalchemy.org/en/<NN>/`; same per-version-rebuild pattern, no rewriter visible.
- **Sphinx itself**: agent couldn't read GitHub HTML contents (flagged as `guess`); likely manual based on visible structure.
- **Cross-project synthesis**: dominant pattern is per-version doc site + author discipline + PR review. The hybrid flat-SSOT + versioned-temporal layout this workbench uses is less common; off-the-shelf tooling for the "active pointer vs frozen citation" distinction does not exist. Sentinel comments are the closest documented analog (intersphinx version-pin behaves similarly, just at the cross-project level).
- **Verdict**: option-1 (path-glob opt-out + manual review) holds up against ecosystem practice. Sentinel comments (option-2) are a low-cost augmentation when dry-run surfaces real mixed files.
