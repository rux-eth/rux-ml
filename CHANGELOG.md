## [Unreleased]

### Added
- **An M9 fit exports its val / test rows; the M9 promote re-fit runs on the batch path** (PR-055; program PR-027 A8 / Q7, build step R3). `rux-ml train` of an M9 problem writes `oos_rows.parquet` as an artifact of the trial — per val / test row the `[m9] row_key_columns`, the prediction the fit scored and the realized target, streamed per day file — with its sha256 in `fold_meta.json` `oos_export` and the trial attribute `oos_export_sha256`; the harness fits the floor on the complement (the train mask rule in `docs/ARCHITECTURE.md`). `registry promote` re-fits an `[m9]` model from per-day batches (the same partition rule and seeds as the trial), bit-identical in prediction to the in-memory re-fit, so a 156-day promote fits the 20 GiB scope.
- **The M9 fits stream per-day batches through XGBoost's native API** (PR-054; program PR-027 A1 / A3 / A11, build step R2). An `[m9]` XGBoost fit of a regression target never collects its source: a `DataIter` hands XGBoost one day file's partition rows at a time (float32 features, the row filter in the scan) into an in-memory `QuantileDMatrix`; val / test are predicted batch by batch; the label diagnostics are summarised by their own pass and the split record / leakage audit come from a per-batch tally. Predictions are bit-identical to the in-memory fit on the same rows. `fold_meta.json` gains `booster` and `ingest` (per-stage seconds); every XGBoost trial records `booster_nthread` / `booster_device`.
  - **Membership change (program PR-027 A4, operator ruling 2026-09-28):** an `[m9]` row-random split is a keyed hash of the row (splitmix64 over the new `[m9] row_key_columns`, seeded by the split seed), not a seeded shuffle — reproducible from the row alone; sizes are the ratios in expectation. An `[m9]` time-block split's rows tied on a boundary stamp now go to the later partition. `make_splits` applies the same rule (tune / promote / the in-memory path). The three M9 problem configs list the harness schema's keys.
  - `split_definition` gains a `seed=` keyword; `[m9]` records add `cuts` (time-block), `membership` (row-random), `train_prefix_last_stamp`.
- **The model manifest records the harness training set's manifest id** (PR-051; program v0.3 D45 #6, ACCEPTANCE C11). New optional `ModelManifest.harness_manifest` (`manifest_id` = the sha256 of the harness set's `manifest.json`, `set_name`, `subtree`, `view_sha256`, `ruxml_data_hash`). `registry promote` reads it before the re-fit from the view program PR-024's materializer writes beside the subtree (`<set>/<subtree>.manifest.json`) and checks it against the set manifest. It refuses with `HarnessManifestError` (exit 2) when the set manifest was rewritten after the view, when the view names another subtree, when the set manifest's copy of rux-ml's `data_hash` differs from the re-fit's, or when an `[m9]` problem's source has no view. Bundles promoted earlier still load (`harness_manifest: null`).
- **Promote refuses a re-fit on other data** (PR-050; PR-040's successor (i); program v0.3 D45 #6, ACCEPTANCE C11). `rux-ml registry promote` hashes the re-fit's `data.source_path` before the re-fit and refuses with `PromoteDataHashError` (exit 2, both hashes, the source and the trial named, no bundle written) unless its `data_hash` equals the one the trial recorded. `data.source_path` is hash-elided, so before this a trial could be promoted by re-fitting on another dataset (a rewritten file, or `--set data.source_path=…`) and nothing noticed. The bundle's `data_hash` is now the checked one (hashed once, not twice).
- **Training-set data-hash bridge** (PR-047; program PR-024 amendment A13, ACCEPTANCE C6 / C11). New verb `rux-ml data bridge --output <sidecar> [--manifest <harness manifest>]`: rux-ml's `data_hash` of one training subtree with every file's sha256, the rux-ml commit SHA and the Polars version; refuses a source whose loaded files (read from Polars) differ from the hashed files; with `--manifest`, the equality test against the harness manifest (exit 2 on any difference). Real-set test `tests/integration/test_training_set_bridge_real.py` (env-driven).
- **The nested-prefix learning curve** (PR-046; program v0.3 D43, ACCEPTANCE C9). New `data.train_prefix_frac` (first fraction of the train window's stamps; val / test fixed) and verb `rux-ml runs learning-curve --study … --output …`: the curve at `[m9] learning_curve_fractions` and D43's "history-limited" verdict against the operator-signed `m9_learning_curve_tolerance_rel`, with the gates sha256; incomparable curves exit 2.
- **Leakage audit and the three M9 regime overlays** (PR-045; program v0.3 D41, ACCEPTANCE C9). Every `train` fit records `leakage` in `fold_meta.json` (stamp-window violations against the fitted partitions; group overlaps per partition pair). An `[m9]` fit is refused with exit 2 if its time-block split shows a fitted stamp within `h_max_ms` of a later row, or its symbol holdout shows a coin in two partitions. New study overlays `m9_regime_row_random`, `m9_regime_time_block`, `m9_regime_symbol_holdout`.
- **M9 honesty metric and the operator-signed keys** (PR-044; program v0.3 D41, D45 #3, ACCEPTANCE C9). New `[m9.gates]` (path, signature, allowed signers, identity, namespace) and `rux_ml.config.m9_gates.load_m9_gates`: verifies the program's signed `gates.yaml` with `ssh-keygen -Y verify`, reads the four M9 keys, refuses on any doubt (exit 2 before the trial row). New `rux_ml.training.honesty.signed_error_honesty` (no-under-deduction fraction; net relative over-deduction). Every `[m9]` fit now records an `oos` block on the held-out test partition (metric, gates sha256, and for markout / walk the honesty verdict). The M9 problems point at the sibling program checkout; they refuse to train until the operator signs the four keys in. `pyyaml` promoted to a direct dependency.
- **Label quarantine: a label is never a feature** (PR-043; program v0.3 D38 #3, ACCEPTANCE C6 / C13; extends PR-040). New required `[data.oracle] label_namespace` (`y__` in `configs/base.toml`). Every training-set build (`train`, `tune`, `registry promote`, `registry score`, the tune objective) refuses a feature column in that namespace (case-insensitive) or listed in `[m9] diagnostic_columns`, with `LabelAsFeatureError` (an `OracleQuarantineError`) and exit 2, before any trial row. Hash-neutral (`data.oracle` is elided). Before this, a `y__` column listed as a feature trained silently.
- **Symbol-holdout split and the embargoed temporal split** (PR-042; program v0.3 D41, ACCEPTANCE C9). New `data.split_kind = "symbol_holdout"` with `data.group_column` + `data.symbol_holdout_seed`: whole coins per partition, each coin's partition fixed by `(seed, coin)` so every target and nested prefix holds out the same coins. New `data.split_embargo` for `time_ordered`: rows whose `t + embargo` reaches the next partition are purged. `train` records the split (`split_definition`: groups per partition, or embargo + purged rows) in `fold_meta.json`. `[m9] h_max_ms`: an M9 problem split `time_ordered` must embargo at least `h_max_ms` (refused at load otherwise). `h_max_ms` is the label's reach (program PR-024 A3: entry latency + resting horizon + longest markout horizon), and the three M9 configs set `h_max_ms = split_embargo = 28801000` (≥ 33 bars at 15 min), not the 4 h markout horizon. All new fields are hash-neutral while unset.
- **M9 problem configs** (PR-041; rux-capital program v0.3 D37 / D45 #3, ACCEPTANCE C9). Three problem files `configs/problems/m9_fill_frac.toml`, `m9_markout_bp.toml`, `m9_walk_bp.toml`: each trains one label (`y__fill_frac` / `y__markout_bp` / `y__walk_bp`) with default-config XGBoost, time-ordered on `stamp_ms`, and lists the other two labels as diagnostics.
  - **New `[m9]` layer** (`M9Config`, `diagnostic_columns`): refuses a target listed as a diagnostic and a diagnostic listed as a feature at config load; optional and hash-neutral while unset (every existing `root_cfg_hash` unchanged, pinned by test).
  - **`rux-ml train`** writes per-fold diagnostic summaries (`n`, `null_count`, `mean`, `std`, `min`, `max`) into `fold_meta.json`; a listed diagnostic missing from the set exits 2.
  - **New metric `brier`** (regression task, minimize): Brier score for a fractional outcome in [0, 1], refusing values outside it; XGBoost / LightGBM / CatBoost early-stop on RMSE for it.
  - Each problem reads its per-target subtree of the training set (program PR-024 A7): `fill/` for `y__fill_frac` and `y__markout_bp`, `walk/` for `y__walk_bp` (`data.source_path = data/m9/training_set/{fill,walk}`; the root is a placeholder until the program's materializer lands).
  - **New `[m9] row_filter_non_null`**: rows with a null or NaN in a listed column are dropped before the split, so train / tune / promote / score see the same rows; the markout problem lists `y__markout_bp` (null on an unfilled order, program PR-024 A9) and trains and scores on filled rows only. A listed column missing from the set refuses the split.
- **Oracle quarantine at ingest** (PR-040; rux-capital program ACCEPTANCE C13). Every training-set read now refuses oracle-derived inputs, raising `OracleQuarantineError` (a `ValueError` subclass). Refused CLI verbs exit 2: `train`, `tune start`/`resume`/`retry-trial`, `registry promote`/`score`, `data hash`/`version`.
  - **What is refused:** a source is refused if it has a column, or nested struct/list/array field, whose name starts with `[data.oracle] namespace` (case-insensitive; hive partition keys included). It is also refused if `[data.oracle] tag_file` sits in any ancestor of the source (the path as given and its resolved path), in any directory inside a directory source, or above the target of any symlink found inside it. Glob sources are refused, and so is a config with no `[data.oracle]` table (fail closed).
  - **Where it runs:** `check_oracle_quarantine` (new, `rux_ml.data`) is called from `load_parquet` and `compute_data_hash`, and as a pre-trial preflight in `train` and `tune`.
  - **Config:** new `DataConfig.oracle`; the values `oracle__` / `ORACLE.tag` live only in `configs/base.toml`, mirrored from the harness. `oracle` is hash-elided, so `data_cfg_hash` and `root_cfg_hash` are unchanged for every existing config. Pinned tests cover the hpo and minimal configs, and the golden_v1 data hash.
  - **API change:** `load_parquet`, `compute_data_hash`, `snapshot` and `data_hashes` gain a required keyword `oracle=`. `rux-ml data hash` now loads the config.
  - **Unchanged:** a clean dataset's frame, `data_hash`, manifest and splits.
  - **Demonstrated** on the real harness oracle store (bare-metal, `22b880e`): both a day-file and a day-directory source exit 2, and the store is unchanged.

### Changed
- **rux-ml computes its logical data hash one file at a time** (PR-053; program PR-027 A2 / build step R1). `_logical_hash` hands Polars one file at a time, scanned with the first file's schema, and holds only one u64 row hash per row. Before, it made one scan and one streaming sort over the whole source, which peaked at 18.0 GiB on the 156-day fill view and left about 400 B per row resident before the fit; per file the same digest peaked at 7.3 GiB. The digest is bit-identical, so no recorded `data_hash`, trial, sidecar or bridge check changes. Every path gets it: `train`, `tune`, `registry promote`, `data bridge`, `data hash`, `snapshot`. A later file whose schema differs from the first's is refused or accepted exactly as the one-scan path did, and a refusal now names the file. New `scripts/check_logical_hash_per_file.py` compares both digests on a real set.
- **The M9 problems train on the `feat__` columns** (PR-049; program v0.3 D38, ACCEPTANCE C10; closes PR-041 Q3). Each problem's `features.spec.numeric_columns` is now the order attributes `p_bp, q_usd, h_ms, side` plus every `feat__` column of its own subtree of the harness schema (`spec/m9_training_schema.json` v2), named explicitly: 32 numeric + `kind` = 33 features for `m9_fill_frac` / `m9_markout_bp` (28 `feat__`), 32 for `m9_walk_bp` (27; `feat__queue_ahead_usd` is fill-only). A test pins each list to the schema. Schema-empty features reach XGBoost as NaN (`missing`). The M9 problems' `root_cfg_hash` changes (the feature spec is part of it); no other config's does.
- **README sync to v0.3** (PR-037). Documents `rux-ml registry score` verb (PR-032) — adds step 7 to the Quick Start (between `registry promote` and `load_model`), inserts new "§7b. Scoring a promoted bundle on its held-out test fold" lifecycle subsection (command examples + receipt schema + on-disk layout + per-split-kind reconstruction strategy), and adds the `registry score` row to the CLI reference table. Closes a v0.3.0 README staleness gap: the v0.3 sprint added the verb but never updated the navigational doc that new users walk through first. No source / test / config changes — README + CHANGELOG only.

### Fixed
- **The bridge's equality test reads the `data_hash` the harness actually writes** (PR-052; fixes PR-047's assumed shape; program ACCEPTANCE C6 / C11). `rux-ml data bridge --manifest` now takes the harness **set manifest** (`<set>/manifest.json`). It compares `subtrees.<subtree>.files` with the loaded files and requires `ruxml_sidecars.<subtree>.data_hash` to equal rux-ml's. It fails closed (exit 2) while the harness has not listed rux-ml's sidecar. PR-047 read a top-level `ruxml_data_hash` that nothing writes, so run against the harness's per-subtree view it passed on the file list alone; that shape is no longer read. `check_bridge` takes `subtree=`.
- **The M9 problems fit the materialized set** (PR-048; program PR-024 B-4). `m9_fill_frac` and `m9_walk_bp` gain `[m9] row_filter_non_null` on their targets (the set writes `no_book` / `below_one_lot` / `alo_expired` rows with NaN targets and a null `y__walk_bp` on ≈ 2 % of walks; before, XGBoost raised "Label contains NaN"). Each problem's `diagnostic_columns` now names only labels of its own subtree (a `walk/` label listed for a `fill/` problem exited 2). `side` moves from categorical to numeric (int8 in the set; `cast(pl.Categorical)` raised). The harness schema is vendored at `tests/fixtures/m9_training_schema.json` and every configured column is tested against it.
